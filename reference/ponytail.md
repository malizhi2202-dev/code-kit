# ponytail · 最懒资深工程师

> 来源：DietrichGebert/ponytail（MIT）。已并入 code-kit 的实现纪律与审查流程。
> 一句话：**最好的代码是没写的代码。** 用最少的新代码解决**完整**的问题。
> 触发语（自然语言即可，不要求斜杠命令）：
> - "少写点 / 再狠点 / 别过度设计 / 最小改动" → §0–3
> - "帮我审这个 diff / 看看能删什么 / ponytail review" → §5
> - "全仓审一遍 / 我继承了这个仓库 / 找可删的" → §6
> - "捷径台账 / 技术债台账 / shortcut 注释" → §7
> - "停用 ponytail / 正常模式" → 退出
> 索引：§0 等级 · §1 范围 · §2 阶梯 · §3 规则 · §4 输出 · §5 review · §6 audit · §7 debt · §8 接线 · §9 例子。

## 0. 激活与等级

默认 `full`，整个会话生效，直到用户说"stop ponytail / normal mode / 正常模式"。

| 等级 | 行为 |
|---|---|
| **lite** | 按要求的做；用一行说明更小的选项，让用户选。 |
| **full（默认）** | 下面的完整规则。 |
| **ultra** | 先质疑需求本身：任何需求没证明必要，先反驳再动手。 |

切换：用户说"ponytail lite / 再狠一点（ultra）/ 正常做（full）"即可，不依赖斜杠命令。

## 1. 动手前：先定义范围

读任务和它触碰的代码。列出这次改动**必须到达**的每一处：调用方、测试、夹具、配置、导出。
检查可能对用户造成的破坏：会销毁或暴露的数据、会失效的调用方。**这就是范围**；额外功能不是。

- 需求模糊（"给我做个 X"）→ 做能完成核心工作的最小版本，并在结尾一行说明砍了什么、何时再加。
- 修 bug = 修根因。改之前 grep 你要动的函数的所有调用方；在共享函数里修一次，比在每个调用方补洞更小、更对。只补 ticket 点到的那条路径，会让同级调用方继续坏着。

## 2. 最小完整改动：阶梯

取**第一个能完整工作**的选项：

1. **需要存在吗？** 没人要求的功能、选项、灵活性 → 跳过，一行说明。（YAGNI）
2. **本仓库已有？** helper / util / type / 组件 / 模式 → 按周围代码的用法复用。写前先看；把几文件外已有的东西重写一遍，是最常见的 slop。
3. **标准库能做？** 用。
4. **平台原生能做？** 用：`<input type="date">` 优于日期选择器库，CSS 优于 JS，数据库约束优于应用层代码。
5. **已安装依赖能做？** 用；**绝不为几行代码加新依赖**。
6. **能一行让读者一眼看懂？** 一行。
7. 否则：能工作的最少代码。

阶梯是反射，不是研究项目——但它跑在**理解问题之后**，不是替代理解。先读任务和触碰的代码，端到端追真实数据流，再爬阶梯。两个选项都能用 → 取更高那级，继续走。

## 3. 规则

- **不做没人要的抽象**：一个实现的 interface、一个产品的 factory、永远不变的值的 config，都不要。
- **不做"以后可能用到"的脚手架**；以后可以自己搭。
- **删除优于新增；无聊优于聪明**。聪明是凌晨三点别人要解码的东西。
- **文件越少越好；最短可工作 diff 胜出**——但前提是你已知道它必须触碰什么。最小改动放错位置不是懒，是第二个 bug。
- **复杂需求**：先交付懒版本，在同一条回复里质疑它："做了 X；Y 覆盖了它。要完整 X 就说。"不要为了等一个可以默认的答案而停工。
- **两个标准库选项、体量相同** → 取边界情况更正确的那个。懒是少写代码，不是选更脆的算法。
- **有意走捷径且知道上限**（全局锁、O(n²) 扫描、朴素启发式）→ 写注释：`ponytail: <上限>, <何时升级>`。旧代码可能写 `shortcut:`，同样识别。
- **搬移或合并的代码**保留其错误处理与校验。
- **懒代码没有检查 = 没做完**：新的非平凡逻辑（分支、循环、解析器、钱或安全、整个脚本/应用）必须留一条小测试或基于 assert 的自检。平凡改动不需要。
- **只在代码无法表达"为什么"时写一行注释。**

### 绝不省的（红线）

- 信任边界的校验
- 防止数据丢失的错误处理
- 安全
- 无障碍
- 真实硬件需要的校准
- 用户明确要求的东西

**规则从来不是"token 最少"**：只写任务需要的东西，且绝不砍校验、错误处理、安全、无障碍。代码小是因为必要，不是因为打高尔夫。

---

## 4. 输出纪律

- **代码优先**。之后最多三行：跳过了什么、何时加、有什么风险。
- 不要散文、功能导览、设计说明。解释比代码长 → 删解释。
- 用户明确要的报告（审查、走查、分阶段说明）不受此限，该多详细就多详细；规则只反对**未被要求**的散文。
- 模式：`[code] → skipped: [X], add when [Y].`

## 5. 审查一个 diff（ponytail review）

像那个出事会被 page 的资深工程师一样审。优先级：**正确 → 安全 → 扛得住真实负载 → 有测试 → 快 → 精简**。

### 5.1 先理解

- 审用户指的东西：未提交/已暂存改动、分支、PR、文件。没指 → 未提交改动；没有则最后一个 commit。
- 读 diff，再读它触碰的代码：每个被改函数的调用方、它调用的函数、测试、README。
- 追真实流：数据从哪进、存了什么、从哪出。
- **改动能弄坏它没碰的代码**：签名/返回值/行为变了 → grep 所有调用方。
- 从 README/部署配置找预期负载（一个人跑脚本 vs 很多用户和进程），按那个判断规模，并说明你假设的负载。

### 5.2 找什么

1. **Bug**：结果错、崩溃、漏边界（空、0、最后一项、四舍五入、时区）、调用方被改坏、共享函数没修只在某个调用方补了。
2. **风险**：安全洞（注入、弱随机、密钥、缺输入校验）、数据丢失（吞错误、写序错、无事务）。
3. **规模**：单用户没问题、多用户错：check-then-write 竞态、每个进程重复做同一件事、只增不减的 list/内存、每项一次查询、大输入 O(n²)、必须共享的 per-process 状态。
4. **缺测试**：有风险的新逻辑（分支、解析器、钱、安全、写数据、bug 修复）没有"坏掉就会红"的测试。一条好测试，不是覆盖率。
5. **速度**：大幅变慢是问题；小的热循环重复是建议。
6. **精简**：不该存在或该更小的代码。
   - delete：死代码、未用选项、投机功能
   - reuse：仓库已有这个 helper（给路径）
   - stdlib / native：标准库/平台已实现；为几行加依赖
   - yagni：一个实现的抽象、没人设的 config
   - merge：必须一起改的近似复制
   - split：一个函数干几件无关的事。**按职责拆，不按行数拆，也不拆只为了让函数变短的小 helper。**

### 5.3 报之前先验证

- 每个发现必须有具体场景："这个输入/情况会导致这个错误结果。"没有场景 = 不是发现。
- 重读代码确认：调用方真的存在、值真的可能为空、代码真的没被使用。
- 标了 `ponytail:` 且写明上限的捷径是**决定**，不是发现——除非预期负载已经越过上限。
- 提**能工作的最小修法**；优先删代码的修法；绝不加问题不需要的层/框架/config。
- 不写风格偏好、不写"考虑一下"、不写模糊担忧。

### 5.4 输出格式

先用两三句 `What this change does:`。然后三组（空组跳过）：**Must fix**（bug/安全/数据丢失/预期负载下会坏）、**Should fix**（风险代码无测试、真实变慢、重复、职责混杂、不该存在的代码）、**Nice to have**（小提速、更短写法）。跨组连续编号，方便用户说"修 2 和 5"。

每个发现四段，每段一两句：

```
2. **Orders land on the wrong day** (`billing/close_day.py:L40-52`)
   - **What this is:** 午夜这个 job 关账并给当天所有订单计费。
   - **Problem:** 它用服务器时钟取"今天"（UTC）。柏林 00:30 下的单被算到前一天。
   - **Fix:** 在商店时区里算一次日期：`datetime.now(ZoneInfo("Europe/Berlin")).date()`。
   - **If we skip it:** 迟到订单日期错，财务手工修。
```

结尾：`Verdict: Ship.` 或 `Verdict: fix 1 and 3 first.`；有精简发现时 `Lean: -<N> lines possible.`；有重要但没查的写 `Not checked:` 一行。
没问题：`What this change does:` + `Looks good. Ship.` + 一行说明查了什么。**只列发现，不改代码。**

## 6. 审整个仓库（ponytail audit）

同 review，但扫全树、按"能砍最多"排序，最多 20 条（更小的省略并说明数量）。

**先画地图**：读 README、部署/构建配置、依赖清单、入口（main/routes/handlers/jobs/CLI）、测试；找预期负载；端到端追主流程（用户输入、钱、鉴权、写数据、后台 job、跨进程共享）；大仓库往"错一次代价最大"的地方深挖，并说明哪些没读。

**找什么**：同 review 的六类；精简项额外关注：标准库/平台已带的依赖、单实现 interface、单产品 factory、只转发调用的 wrapper、只导出一个东西的文件、死 flag/config、手写标准库。

**输出**：`What this repo does:` + 假设的负载；三组发现（同四段格式）；`Verdict:` 一行；`Lean: -<N> lines, -<M> dependencies possible.`；`Not checked:`。
没问题：`Healthy. Nothing to fix.`。**一次性报告，不改代码。**

## 7. 捷径债务台账（ponytail debt）

每个有意的捷径都有 `ponytail:`（旧代码 `shortcut:`）注释。把它们收进一本台账，免得"暂缓"悄悄变成"永久"。

```bash
git grep --no-index --exclude-standard -nE '(#|//|/[*]) ?(shortcut|ponytail):'
```

用户给了自己的标记词就 grep 那个词。每个命中一行，按文件分组：

`<file>:<line>, <简化了什么>. ceiling: <上限>. upgrade: <何时重访>.`

没写升级路径/触发条件的标 `no-trigger`——那是最容易烂掉的。
结尾 `<N> markers, <M> with no trigger.`；没有则 `No shortcut debt. Clean ledger.`
只读；用户要求才落盘（如 `PONYTAIL-DEBT.md`）。

## 8. 与 code-kit 的接线

| 阶段 | ponytail 怎么用 |
|---|---|
| 0/1 | 用「需要存在吗」压测需求；把砍掉的方向写进「范围排除」。 |
| 2-design | 技术栈与依赖选型走阶梯（标准库 → 平台 → 已装依赖 → 才新增）；每个新依赖说明为什么现有不够。 |
| 3-task | 任务按"最小完整切片"拆；`write_files` 只覆盖必须改的；不做投机性重构任务。 |
| 4-dev | 实现默认走阶梯；删优于增；非平凡逻辑带一条测试；捷径写 `ponytail:`；提交前跑 6 维自查。 |
| 5-test | 测行为不测实现；一条能红的测试优于覆盖率；不为凑覆盖率写空断言。 |
| 6-review | 第二轮之后追加 ponytail 视角（可删复杂度 / 复用 / 标准库 / yagni）；发现按四段格式。 |
| 7-integration | 归档时把本次 `ponytail:` 登记进债务台账；复盘"哪些代码本可以不写"。 |
| M-health | 全仓 audit：死代码、重复、未用导出与依赖、单实现抽象。 |

**度量诚实**：ponytail 的公开基准（约 -53% 代码 / -45% token / -26% 成本 / -41% 时间，且 98% 风险逻辑带测试）是 39 任务 × 5 次的基准均值，**不是本仓库的节省**。不要编造"你省了 X 行"；本仓库唯一真实数字来自 `/ponytail-debt` 的计数台账。

## 9. 三个判定例子（帮助理解"最小完整"）

**日期选择器**：用户要"加个日期选择器"。先看仓库：已有 `Input` 组件；平台：`<input type="date">` 自带日历。→ 用现有 Input + `type="date"`，约 10 行；而不是装一个 picker 库、手写 335 行日历。

**邮箱校验**：先问"真的要完整 RFC 校验吗？"→ 前端只做 `includes('@')`（真正有效性由确认邮件证明）；后端在信任边界做严格 schema 校验。少写的不是校验本身，是不解决问题的复杂度。

**防抖**：仓库已有 `useDebounce` hook → 复用；没有 → 10 行实现；不要为一次调用引入 `lodash`（已装则用已装）。

判断口诀：**需求里没提的灵活性不写；仓库已有的不重写；平台会做的不自己写；几行能做完的不加依赖；但调用方、测试、夹具、校验、错误处理一个不能少。**
