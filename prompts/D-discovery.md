# D-discovery — 议题发现循环（事实文档驱动）

> 用户想调研/讨论/找改进点，但还没到写 CHANGE 的程度时走本流程。
> **一句话**：根据事实文档拆子议题；拆出来就必须讨论（头脑风暴、竞品分析、结论、专家团）；这个过程最多重复三轮；实在拆不出就停，不重复。
> 全程**只读、零代码改动**；结论过**人工审核门**才落盘。

---

## 硬性约束（违反即失败）

1. **零代码改动**：不改任何源码/配置/测试/脚本；不引用 `4-dev`；不"顺手改"。结论若涉及代码，只输出《建议改动清单》（改哪个文件、改什么、为什么），执行走新 CHANGE。
2. **事实文档是唯一拆解依据**：每个子议题、每条结论必须能指回具体事实（文件路径、代码位置、配置项、数据、用户原话）。无依据不写、不列、不猜。
3. **人工审核门**：结论先以对话形式呈给用户；用户明确说"通过 / 审核完毕 / OK"之前，**严禁写任何文件**。
4. **落盘后置**：审核通过才一次性沉淀该议题产物；未过审核门的议题文件不存在。
5. 审核不通过 → 带修改意见回到第①步重跑，不写盘。

## 产物位置

`.specs/<change-id>/discovery/<议题slug>/`（change-id 可用占位 `disc-<日期>`，后续正式立项时引用）。

---

## 第 0 步 · 扫描事实文档 → 拆子议题（强制第一步）

### 0.1 只读收集事实

- **流程工件**：`.specs/` 下全部 CHANGE/REQUIREMENT/DESIGN/TASK/REVIEW、`.specs/CONTEXT.md`、`.specs/LESSONS.md`、根 `STATE.md`
- **代码与配置（只读）**：目录结构、关键模块入口、配置文件、依赖清单、README
- **数据与材料**：用户提供的文件、日志、指标、用户原话里的事实
- **缺失声明**：读不到就明说"缺什么"请用户补——**不凭空拆解**

### 0.2 拆解规则

- 拆出 **2-5 个**子议题，每个必须是能独立走完五步的具体问题
- **每个子议题必须标注依据**：`依据：.specs/x/REQUIREMENT.md §2` / `依据：src/a/b.ts 的 X 逻辑` / `依据：用户原话"…"`
- 拆解维度：现状痛点 / 用户价值 / 技术可行性 / 竞品差距 / 风险点
- **反例**：无依据的"要不要做个 XX"不许列为子议题

### 0.3 拆不出的分支

实在拆不出任何**有事实依据**的新子议题 → **停止循环，不重复**：说明"已无新子议题"，输出已有汇总与《建议改动清单》，问用户是否进入下一阶段（进入下一阶段 ≠ 重复循环）。

---

## 五步讨论流程（每个子议题必须走完，不许跳步）

> 拆了子议题就要讨论——不允许跳过讨论直接给结论。

### ① 头脑风暴发散（技法内联，无外部依赖）

先静默发散再收敛：每轮 8-15 个候选方向，按"影响面 × 可行性"初排。可用技法（按需选 2-3 种，说明用了哪种）：

- **SCAMPER**：对现状逐问 替代/合并/调整/修改/他用/消除/重组
- **六顶帽**：事实→情绪→风险→价值→创造→流程 六视角各出 2 条
- **逆向**：问"怎么把这个问题弄到最糟"，倒推出防御点
- **假设反转**：把一条既有假设反过来说，看是否仍成立
- **类比迁移**：从第 0 步事实里找相邻模块的成熟做法平移过来

必须带上第 0 步的事实依据作为约束（每个候选标注它回应哪条事实）。

### ② 竞品与其他产品做法分析

对 Top 3-5 候选逐个查：其他产品怎么做、成熟模式、踩过的坑。

- **能联网**：真实检索（遵循 R11.1 探测），给出来源链接
- **不能联网**：基于既有知识作答，**显式标注"未联网验证"**
- 每个候选记录：产品名 / 做法 / 可借鉴点 / 不可取点

### ③ 总结结论与建议

自己完成。产出：**结论**（推荐 1-3 个方向 + 引用①②证据）、**建议**（每方向一句话落地路径）、**否决记录**（被否方向 + 理由）。
结论打磨用一轮批判技法（任选其一）：苏格拉底（逐条假设反问）/ 第一性原理 / 预演失败（假设上线失败倒推）/ 红队（专攻最弱一环）。

### ④ 专家团评审

复用 code-kit 角色体系，组 **3 人快速评审团**（非完整 Gate）：`R-高级产品经理`（用户价值）+ `R-前端架构师` 或 `R-研发负责人`（技术可行性）+ `R-领域专家`（业务合理性；无对应领域时用 `R-资深用户评测员` 代替）。每位给出：同意 / 有保留 / 反对 + 一句话理由（R13.3 投票格式）。

### ⑤ 人工审核门（硬门禁）

以对话形式呈现：

> **议题**：…（依据：…）
> **结论**：推荐 X、Y
> **专家团**：PM 同意 / 架构有保留（理由） / 领域 同意
> **影响面**：…（涉代码则附《建议改动清单》，并声明"本流程不执行代码改动"）
> **建议下一步**：…

明确问：**"审核是否完毕？通过则落盘并进入下一个。"**

| 用户回应 | 动作 |
|---|---|
| 通过 / 审核完毕 / OK | 一次性写盘 → 进入下一个（子议题或阶段） |
| 有修改意见 | 带回意见回到 **①** 重跑本子议题，不写盘 |
| 沉默 / 不确定 / 追问细节 | 停在 ⑤，不写盘，不进下一个 |

---

## 三轮重复规则

**一轮 = 一次"扫描事实 → 拆子议题 → 所有子议题走完五步并过审核门"**。

| 轮次 | 做什么 |
|---|---|
| 第 1 轮 | 扫描事实 → 拆主议题的子议题 → 逐个走五步 + 过审核门 |
| 第 2 轮 | 重新扫描（含上轮已通过结论）→ 再挖下一层子议题 → 同上 |
| 第 3 轮 | 同上 |

每轮结束重新执行第 0 步拆解判断：**拆得出**（有事实依据）→ 继续；**拆不出** → 停止，不重复——不硬凑、不擅自开第 4 轮、不重炒已讨论过的冷饭。

## 产物落盘（仅审核通过后）

```
.specs/<change-id>/discovery/<议题slug>/
  ├── 00-subtopics.md         子议题清单 + 每个的事实依据 + 轮次记录
  ├── <子议题slug>/
  │     ├── 01-brainstorm.md
  │     ├── 02-competitive-recon.md
  │     ├── 03-conclusion.md
  │     ├── 04-panel-verdict.md
  │     └── 05-review-record.md   人工审核记录（审核原话/时间点）
  └── 99-roadmap.md           三轮汇总结论 + 建议改动清单
```

`05-review-record.md` 是"已审核"的唯一证据；未过审核门的议题，其文件不存在。

---

## 与主流程的衔接

- 议题通过审核且要立项 → 把 `99-roadmap.md` 作为输入引用，走 `0-change` 起 CHANGE.md（CHANGE 的"why/what"直接引用 roadmap 结论）
- 只想留档不立项 → 产物留在 discovery/ 目录，STATE.md 记一行"已留档议题 <slug>"
- 与 `S-align` 的关系：D-discovery 产出建议、不改代码；S-align 检测五层漂移。两者都只读，可任意先后
