# 多 agent 自动化协作

> 规则依据：`RULES.md` R17（协作）/ R18（澄清式人工介入与沉淀前置）。
> 适用：任务进入 `3-task` 之后（拆解完成、`<auto>` 已投票），或以常驻 agent 模式挂机运行。

---

## 1. 七类 agent

| # | agent | 生命周期 | 职责 |
|---|---|---|---|
| ① | 主拆解/调度 | 每 change 一个 | 顺序跑 0→1→2(→2a)；拆 3-task + 波次 + `<auto>`；按波次派发；汇总；触发 S-align |
| ② | 子开发 | 每 task 一个 fresh context | 在 read/write 边界内完成单 task；自检 done；完成即报告，不自行测试 |
| ③ | 测试 | 每 task 完成即介入 | 跑 verify + AC 抽查；给通过/失败 + 证据；不等波次收尾 |
| ④ | 日志扫描 | 常驻 | 扫全部 agent 日志判错；满足准入三条件才放行修复 |
| ④' | 修复 | 按需 | 修 bug / 重跑 verify / 回滚越界 |
| ⑤ | 自动提交 | 常驻 | 阶段产物齐才 commit；落盘前过人工把关 |
| ⑥ | 自动拉齐 | 常驻 | 拉 git、扫任务/结论来源、发现漂移触发 S-align |

分工：主 agent 只拆不打；前 3 阶段不可并行；只有 3-task 之后的任务波次可并行。

## 2. 状态机

```
pending → in-flight → done(自检) → testing → passed → reviewed → 待提交
                          │            │
                          └─ failed ───┘ → 修复 agent（满足准入）→ 重跑
```

`done ≠ 完成`：必须 verify 通过 + review 通过。

## 3. 人工介入：澄清触发，不是固定关卡

每个阶段收尾时跑推进检查：

```
阶段工作完成？
  ├─ 否 → 继续做
  └─ 是 → 沉淀输出物（工件落盘 + STATE 状态行 · R18）
          ├─ 未落盘 → 先补盘，禁止推进
          └─ 已落盘 → 有澄清需要？（歧义/偏好/纠正/把关）
                      ├─ 无 → 直接进入下一阶段（不问"要继续吗"）
                      └─ 有 → 停下一次性问清 → 解决后推进
```

**直通条件** = 上下衔接清楚 + 方案清楚：上游工件齐全无歧义、方案无平票、verify 可机判 → 落盘即走。

**澄清四类**：① 歧义（多套合理解法/平票）② 偏好（审美/取舍）③ 纠正（用户看过产物不满意）④ 把关（不可逆动作：提交、归档、破坏性变更）。
③ 不是主动停顿：产物生成后正常直通，用户回头说不满意才触发纠正循环。

**法定暂停点**：`<auto>false</auto>` 任务执行前；议题 ⑤ 人审门；违规处理协议。其余不设"第 N 阶段必须停"。

## 4. 日志扫描判定

- **E1 边界越界**（`write_files` 外出现 diff）→ R6.5 拦截，登记回滚
- **E2 verify 失败** → 转修复（满足准入）
- **E3 幻觉产物**（引用不存在的文件/接口）→ 标记重做该 task
- **E4 中途崩溃**（未到 done）→ 挂起，波次收尾统一重派
- **E5 依赖等待**（上游未完成）→ 正常，不算错误
- **修复准入三条件**：任务 done + 无下游依赖 + 产物完全可读；缺一挂起。

## 5. 提交标准（缺一不提）

| 凑齐产物 | commit 主题 |
|---|---|
| `CHANGE.md` | `docs(spec): change <id> 立项` |
| `REQUIREMENT.md` + `CONTEXT.md` 更新 | `docs(spec): <id> 需求与术语` |
| `DESIGN.md`（含 §0） | `docs(spec): <id> 技术设计` |
| `UI-DESIGN.md` | `docs(spec): <id> UI 设计` |
| `TASK.md`（含 `<auto>`） | `docs(spec): <id> 任务拆解` |
| 某波次全部 task 通过测试 + review | `feat(<id>): 波次 N 完成` |
| `TEST.md` 矩阵 + 执行记录 | `test(<id>): 测试矩阵执行` |
| `REVIEW.md` | `docs(spec): <id> 双轮审查` |
| `ALIGNMENT.md` + 归档套件 | `chore(spec): <id> 对齐归档` |

中间态不提交；commit 生成 → 人工把关 → 落盘；堆积未确认的在 `STATE.md` 登记提醒。

## 6. 自动拉齐与 S-align

拉齐 agent 是 S-align 的**常驻前置哨兵**，不是替代：

| 层 | 拉齐 agent | S-align |
|---|---|---|
| 触发 | 定时/事件式（git 新提交、wiki 新结论、记忆库新条目） | 显式调用（7-integration 前强制） |
| 扫描 | git + 任务/结论来源 + 产物 + 代码 | 五层（代码/原型/活文档/决策留痕/执行留痕） |
| 动作 | 登记可能不一致，产出候选漂移清单；轻微文档漂移可直接修 | 按 D1–D6 出正式 `ALIGNMENT.md` + 合并清单 |
| 代码 | **永不改代码**；涉代码升级人工 | 同样永不改 L1 代码，合并需用户确认 |

来源冲突时以**最近 git 提交**为权威时间线，其余作补充证据并登记冲突。

## 7. 降级策略（无后台常驻能力）

纯对话式工具（含 DSH 默认形态）：

| 本架构 | 降级实现 |
|---|---|
| 常驻日志扫描 | 每个波次收尾，主 agent 跑一轮 §4 扫描 |
| 常驻自动提交 | 每凑齐 §5 一行产物，发起一次人工把关 |
| 常驻拉齐 | 进 7-integration 前跑一次 S-align（本来就是 R15 强制） |
| 子开发/测试/review | 逐 task 顺序 4-dev → verify → 小节 review |

DSH 有 `subagent` / `workflow` / `create_goal`：波次并行用 `subagent`，≥3 个同构任务用 `workflow`，跨会话长目标用 `create_goal`；前 3 阶段顺序做，不要扇出；每个 task 完成后主 agent 亲自跑 verify 并贴输出。
